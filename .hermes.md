# Relay Rider Hermes Engineering Rules

Relay Rider is an institution-funded Transportation Demand Management research-beta product. Describe proposed, modeled, observed, and calculated evidence accurately. Do not frame the product as ride-hailing, taxi, live dispatch, instant pickup, guaranteed transportation, or an unrestricted public rideshare marketplace.

## Scope and branch boundary

- Work only in an isolated Git worktree on a `hermes/` or `hermes-subagent/` branch.
- Fetch, edit, test, commit, push the assigned development branch, and prepare PRs targeting `main` when authorized by the task.
- Never commit or push to `main`, force-push, rewrite published history, delete remote branches, merge PRs, bypass CI, change repository administration, or alter GitHub credentials, secrets, deploy keys, collaborators, rulesets, or environments.
- Do not use `git reset --hard` or destructive `git clean` without founder approval.

## Production and credential boundary

- Never deploy production, run production workflows, mutate production Supabase/PostgreSQL data, apply production migrations, rotate credentials, or print/read credential material to obtain values.
- A required production action is a stop condition. Report the exact action, target, reason, branch and SHA, completed tests, rollback path, and risk; request founder approval.
- Preserve secret redaction. Do not add credentials to the repository, worktrees, commits, issues, PRs, tool output, or logs.

## Product, data, and security invariants

- Preserve institution/tenant isolation, least privilege, RBAC, participant/admin separation, data minimization, approximate zones before precise locations, provenance, withdrawal/suspension semantics, accessibility, and no cross-tenant leakage.
- PostgreSQL is authoritative where the canonical backend is applicable. Preserve `relay_app` schema placement, migration provenance, canonical commuter records, API contracts, and the Green Wallet canonical contract.
- Rule 2202 calculations are deterministic. Do not change formulas, scoring weights, evidence classifications, or regulatory interpretation without explicit scope, tests, TDM review, and independent review. Never present research-beta calculation output as regulatory certification.

## Development team protocol

- Engineering Lead defines scope, prohibited actions, likely files, test evidence, and acceptance criteria before delegation.
- Implementation workers use narrow assignments. A worker never approves its own work.
- Security reviews authorization, tenant isolation, secrets, migrations, and production boundaries when relevant. QA reruns acceptance evidence from a clean worktree. An independent reviewer examines the final diff and evidence.
- Report exact commands and observed outcomes. Failures, skipped checks, environmental blockers, and limitations must be stated plainly; never fabricate passing evidence.

## Required validation

Use repository commands appropriate to the change. For frontend changes: `npm ci`, `npm run check`, `npm test`, `npm run security:check`, and `npm run build`. For backend changes: Django system checks, migration drift validation, and backend tests; use disposable PostgreSQL and `relay_app`/Rule 2202 vertical-slice checks for database or domain behavior.

The configured Relay Rider pre-tool policy hook is a second enforcement layer. It must remain fail-closed for terminal, file-write, patch, file-read, and file-search calls. Do not remove, weaken, or bypass it.

## Status evidence

Before PR readiness, report branch, base and final SHA, files changed, validations with results, security/tenant implications, migrations and rollback when applicable, blocked actions, independent-review state, known limitations, and founder approval required. Founder approval is required for merge.
